Closes #701

## Summary

The security principle this issue targets — never handle private keys; validate every signed envelope against the recorded settlement intent before submission — is already the architecture of this repo (`src/services/stellar.ts`, `src/services/settlement-xdr.ts`). This PR audits every path where an envelope enters the API and closes the coverage gap the audit found, so the guarantee is *proven at the route boundary*, not only inside mocked service tests.

## Audit result — zero private key handling

`grep` over `src/` confirms the only secret-key use is the server's own SEP-10 signing key (`src/services/sep10.ts`, `config.SEP10_SIGNING_SECRET`), which is the server's identity, not a user key. There is no `Keypair.fromSecret`/`fromRawSeed` on user data anywhere, no user private key is ever accepted as input, stored, or logged. Logging redacts `privateKey` fields (`src/plugins/logging.ts`, `src/serializers.ts`). Unsigned XDR is built in `src/services/stellar.ts#buildPayment` — the wallet signs, the API only verifies signatures already on the envelope.

## What was already enforced (verified, unchanged)

- `validateSettlementXdr` (`src/services/settlement-xdr.ts`) rebuilds the expectation from the **persisted settlement row only** — never from anything the client sent — and checks: parseability, fee-bump rejection, time bounds vs recorded expiry, transaction source, exactly one payment operation, fee bounds, operation source, destination, asset code **and issuer**, amount, memo, and a signature verifying against the source account for our network passphrase.
- It runs in `POST /settlements/:id/confirm` and `POST /api/settlements/execute` **before** the envelope is persisted, and again in the worker (`src/worker/index.ts`) at submission time, so a stale or tampered envelope never reaches Horizon.
- Treasury confirm additionally binds the submitted envelope to the `intendedTxHash` computed when the unsigned XDR was built (`src/routes/treasury.ts`).

## Gap closed

`POST /api/settlements/execute` is the money-moving endpoint, but its existing tests (`tests/settlement-execute-idempotency.test.ts`) mock `validateSettlementXdr` — correct for testing idempotency, but it means no test proved the route itself rejects a tampered envelope against the real recorded intent. This PR adds that proof.

## Changes

New `tests/settlement-execute-xdr-validation.test.ts` builds and signs **real Stellar envelopes** with locally generated keypairs (the way a wallet would — the test, like the API, never possesses the payer's key beyond the envelope construction) and exercises the route end-to-end:

**Accepted:** the envelope matching the recorded intent is accepted (202), persisted to the worker via `transactionXdr`, and marked `submitted`.

**Rejected with 400 XDR_MISMATCH / XDR_MALFORMED, nothing persisted:**

- destination swapped for a different account
- amount changed after signing
- asset swapped (XLM → USDC)
- memo no longer referencing the settlement's short code
- transaction source that is not the settlement's payer
- envelope signed by a third party
- unsigned envelope
- fee-bump wrapper
- malformed XDR
- envelope whose validity window outlives the recorded intent expiry (a wallet may not extend the server's deadline)

**Safety properties also asserted:**

- the envelope is never echoed back in any error response or audit record (only the stable field-level reason)
- a validation failure is audited (`settlement.execute.validation_failed`) for later review
- a tampered envelope never advances the settlement status or writes `transactionXdr`

## Acceptance criteria

- [x] Settlement validation utility inspects transaction envelopes for correct source, destination, and asset amounts (`validateSignedXdr` → `assertMatchesIntent`)
- [x] Rejection of signed XDRs that deviate from the recorded group expense settlement intent — now proven at the `/api/settlements/execute` route boundary with real envelopes
- [x] Comprehensive unit tests verifying XDR intent validation with valid and tampered transactions (joins the existing `tests/settlement-xdr-validation.test.ts`, `tests/xdr.test.ts`, `tests/settlement-confirm-xdr-validation.test.ts` suites)
- [x] Zero private key references or handling in codebase — audited and documented above; tests sign locally exactly as a wallet would
