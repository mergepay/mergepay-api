## Summary

The issue's acceptance criteria are mapped to this repo's actual conventions, which had already evolved past the issue's original file paths. This PR verifies the implemented behaviour, fills the two remaining acceptance gaps (boundary tests and contract documentation), and leaves the existing, tested implementation untouched.

## Where the criteria live in this repo

- **Zod query validation** — the issue names `src/schemas/expenses.ts`; this repo keeps per-feature validation in `src/validations/` and `src/services/`. The expense list query schema is `expenseListQuerySchema` in `src/services/expenses.ts`, and it extends the shared `paginationQuerySchema` from `src/lib/pagination.ts` (cursor / limit / order), exactly the "consistency with existing pagination patterns" the issue asks for.
- **Query logic** — `listGroupExpenses` in `src/services/expenses.ts`, called by `GET /groups/:id/expenses` in `src/routes/expenses.ts` after a `requireMembership` check. There is no raw Prisma builder in the route; the service composes the `where` from group scope + filters + cursor.
- **Filters** — `asset` (XLM/USDC), `status` (PENDING/SETTLED, derived from per-share settlement state since `Expense` has no status column), `startDate`/`endDate` (inclusive, validated, reversed range → `INVALID_RANGE`), and opt-in `includeTotal`.
- **Pagination metadata** — returned in the response body envelope as `meta` (`nextCursor`, `hasMore`, `limit`, `order`, plus `total` when requested), matching every other list endpoint in the API.

## Changes

### 1. Pagination boundary tests (`tests/routes/expense-pagination-boundaries.test.ts`, new)

The filters and general contract were already covered (`tests/routes/expenses.test.ts`, `tests/pagination-contract.test.ts`), but the edges were not. Now pinned:

- `limit=0` and negative → `VALIDATION_ERROR`, no query runs
- `limit=MAX_PAGE_SIZE` (100) accepted; `limit=101` → `VALIDATION_ERROR` — never a silent clamp
- non-numeric and non-integer limits rejected
- default page size is the shared `DEFAULT_PAGE_SIZE` (50)
- **bounded-read contract**: the query takes exactly `limit + 1` rows (page + lookahead), even when the table holds thousands of rows — the property that keeps large groups cheap
- exact-limit result set → full page, `hasMore: false`, `nextCursor: null`
- limit+1 rows available → sliced to limit, `hasMore: true`, cursor issued
- one-row group → single item, empty cursor
- `meta` echoes the effective `limit` and `order`; `order=asc` produces the `(createdAt asc, id asc)` orderBy; invalid `order` rejected

### 2. Documented the expense list filters (`docs/api-contract.md`)

The filters were implemented and tested but absent from the API contract. A new "Expense list filters" subsection under the existing Pagination section documents `asset`, `status` (with the every-share-settled semantics), the inclusive date range and its `INVALID_RANGE` error, and the opt-in `includeTotal` (and why the total excludes the cursor so it stays stable across pages).
